4. **N7 (course sur l'offset) non corrigé.**

5. **L7 incomplète.**

## Régressions introduites

### R-1. L9 : le cache par saison tronque la recherche des replays plus anciens — CONFIRMÉ (exécuté)
- Fichiers : `src/lib/bv.ts:151-173`, `src/lib/db.ts:370-377` (`ORDER BY date_utc DESC`), `src/lib/ingest.ts:120-136`
- Sévérité : **élevée** (fonction principale : la découverte des replays)
- Symptôme :
  - `fetchSeasonListing` arrête le parcours dès qu'une page est entièrement plus ancienne que `oldestUsDate` (`:163`), puis met en cache **ce résultat partiel** sous la seule clé `season`. Le commentaire « (presque) le même résultat » est faux.
  - `syncVideos` traite les matchs du plus récent au plus ancien. Le 1er appel (match d'hier) ne remplit que la page 1, voire la 2.
  - Pour les matchs suivants (jusqu'à J−21), le cache renvoie la liste tronquée. `matchListingEntry` ne trouve rien, d'où `reason: 'replay non listé'` et `markVideoChecked`.
  - Au cycle suivant (2 h plus tard, TTL de 30 min expiré), le même ordre reproduit le même échec tant qu'un match récent sans vidéo reste en tête.
  - Exécuté avec un `fetch` simulé (pages datées 15, 10 et 5 nov.) : `fetchSeasonListing(2026,'2026-11-14')` fait 2 requêtes. `fetchSeasonListing(2026,'2026-11-03')` renvoie ensuite le cache sans le 5 nov.
- Correctif : stocker aussi dans le cache la date la plus ancienne couverte (`oldestCovered`) et la page atteinte. Ne servir le cache que si `oldestCovered <= oldestUsDate`, sinon reprendre le parcours à la page suivante et fusionner. Variante plus simple : un cache par page (`season:page`), comme proposé en 1re revue. Ajouter un test avec deux dates.

## Nouveaux findings

### N-C1. CSRF : contrôle du Content-Type contournable — CONFIRMÉ (exécuté)
- Fichier : `src/app/api/matches/[id]/sync/route.ts:94-97`
- Sévérité : **moyenne** (en configuration par défaut, `SYNC_WRITE_ORIGINS` vide, c'est la seule défense)
- Symptôme :
  - `ctype.includes('application/json')` accepte `text/plain;charset=application/json`. Pour le navigateur, l'essence MIME est `text/plain` : la requête est « simple », sans preflight.
  - Un site tiers peut donc faire `fetch(url, {method:'POST', mode:'no-cors', headers:{'Content-Type':'text/plain;charset=application/json'}, body:'{"global_offset":3600}'})`, ou lancer `analyze`.
  - Exécuté sur le serveur standalone, avec une **copie** de la base : `Origin: https://evil.example` donne **200**, et `global_offset` passe à 7. `text/plain` nu donne bien 415.
- Correctif : `const essence = ctype.split(';')[0].trim(); if (essence !== 'application/json') return 415;`. En complément :
  - refuser tout `Origin` différent de l'hôte servi, même si la liste est vide (`new URL(origin).host === req.headers.get('host')`) ;
  - ou exiger un en-tête personnalisé (`X-Requested-With`), qui force un preflight.

### N-C2. `isOriginAllowed` : « la même origine est toujours autorisée » n'est pas implémenté — CONFIRMÉ (lecture et exécution), exploitabilité À CONFIRMER
- Fichier : `src/lib/api.ts:116-122`
- Sévérité : faible à moyenne
- Symptôme :
  - Le code n'autorise pas `Origin == hôte de la requête`. Il autorise **toute** origine dès que l'hôte de `req.url` figure dans la liste.
  - En test unitaire (`req.url = http://nas.local:3000`, liste = README), `Origin: https://evil.example` est **accepté**.
  - En standalone, `req.url` vaut `http://0.0.0.0:PORT` (mesuré : le contournement n'apparaît que si `0.0.0.0` est listé). Il n'est donc pas exploitable en Docker tel quel, mais il le devient si Next construit `req.url` depuis `Host` (`next dev`, autre déploiement).
  - Inversement, la promesse documentée n'est pas tenue : un utilisateur qui accède par un nom non listé reçoit 403 sur sa propre UI.
  - README `:129` : l'exemple `192.168.1.16` laisse croire à une IP **cliente**. C'est en réalité l'adresse du **serveur**, puisque l'Origin est celle de la page.
- Correctif : `const self = req.headers.get('host'); if (self && o === self) return true;` et supprimer le bloc `:116-122`. Clarifier le README.

### N-P1. Proxy segment : après une redirection, les statuts 416 et 4xx sont lus sur la mauvaise réponse — CONFIRMÉ (lecture), latent
